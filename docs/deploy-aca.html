Deploy ChessBuddy to Azure Container Apps

Two container apps on the free Consumption plan: a public web app and a private Stockfish engine that can run at least two engines at once. Accounts live in your Azure SQL free-tier database.

Azure portal Docker Hub via GitHub Actions About 45 minutes the first time

Overview

  • chessbuddy-web is the Dockerfile in the repo root: Express API, the built React app and sign-in.
  • chessbuddy-engine is the http target of docker/mcp-stockfish.Dockerfile: the same mcp-stockfish engine you run locally, behind a small MCP-over-HTTP gateway. Each replica runs ENGINE_POOL_SIZE (2) engines, so a grade and the bot's move run at the same time; a third request at once starts a second replica.
  • The engine's ingress is limited to the environment, so the internet can't reach it. A shared token protects it as well.
  • The web app only touches the database when an account other than the owner signs in: the owner's password is checked against a hash the app already has. Sessions are signed cookies that also carry the account's VIP flag, so the free-tier database can pause while you play.

Before you start

  • An Azure subscription with billing set up (pay-as-you-go). The Container Apps free grant applies automatically.
  • Your Azure SQL free-offer database: server name, database name, and a SQL user and password.
  • A Docker Hub account (the free Personal plan is enough) and this repo on GitHub.
  • Node.js and this repo with npm install done, for the secrets and the password hash. Docker Desktop is only needed to build images by hand.
  • An Anthropic API key for Explain (grading and the bot work without one).

In the commands below, replace <docker-user> (your Docker Hub username) and the other orange values with yours.

1 Prepare secrets

Generate two random values: one for SESSION_SECRET (signs session cookies) and one for ENGINE_TOKEN (shared by the web app and the engine). Run this twice and keep both outputs:

node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"

Get the database connection string: in the portal open your SQL database → Settings → Connection strings → ADO.NET (SQL authentication), copy it and put your password in place of {your_password}. It looks like:

Server=tcp:<server>.database.windows.net,1433;Initial Catalog=<database>;User ID=<user>;Password=<password>;Encrypt=True;

Optional, for how often each move is played in Learn openings: a Lichess token. The Lichess opening explorer only answers signed-in accounts, so sign in to (or create) a free Lichess account and open lichess.org/account/oauth/token → New personal API access token. Give it a description such as ChessBuddy, leave every scope unticked, create it and copy the token (it starts with lip_).

These values (session secret, engine token, connection string, Anthropic key, Lichess token) only go into Container Apps secrets in step 6. Don't put them in an image or commit them.

2 Open Azure SQL to Azure services

  1. Open the SQL server (not the database) and go to Security → Networking.
  2. Set Public network access to Selected networks.
  3. Under Exceptions, tick Allow Azure services and resources to access this server, then Save.

Container Apps on the Consumption plan have no fixed outbound IP, so this exception is how the web app gets through. It admits any Azure address, so keep a strong SQL password.

To also sign in from npm run dev against this database, add your own IP under Firewall rules and put the connection string in your local .env as SQL_CONNECTION_STRING.

No table to create by hand: the owner account kviiilyn37_ isn't stored in the database, and the app creates chessbuddy.Users (or adds its IsVip column to a table made before it existed) on the first sign-in that looks an account up. The script in step 11, which adds accounts, does the same first.

3 Publish the images to Docker Hub

The workflow in .github/workflows/ci.yml does this on every push to master: it typechecks, runs the tests, builds both images for linux/amd64 and pushes them to <docker-user>/chessbuddy-web and <docker-user>/chessbuddy-engine. It only needs a Docker Hub token.

  1. In Docker Hub, open your avatar → Account settings → Personal access tokens → Generate new token. Description github-actions, Access permissions: Read & Write. Copy the token; it's shown only once.
  2. Generate a second token the same way with Public Repo Read-only, description container-apps, and keep it for steps 4 and 5.
  3. On GitHub, open the repo's Settings → Secrets and variables → Actions.
    • Variables tab → New repository variable: name DOCKERHUB_USERNAME, value your Docker Hub username.
    • Secrets tab → New repository secret: name DOCKERHUB_TOKEN, value the Read & Write token.
  4. Push to master, or open Actions → CI → Run workflow. When the run is green, its summary lists the pushed tags.
TagWhen
sha-<commit>Every push: the first 7 characters of the commit, for example sha-1e322e2. Both images of a commit get the same tag. Use these in Container Apps.
latestEvery push to master
1.2.0When you push a git tag such as v1.2.0

Docker Hub creates both repositories on the first push, public unless you changed Default privacy in your Docker Hub settings. The images hold no secrets (.dockerignore keeps .env out), and the code is on GitHub anyway. Pull requests build the images without pushing them.

Why a sha tag and not latest: a replica that starts from zero may pull its tag again, so with latest a cold start could switch to a newer image without a new revision, and the web app and engine could end up on different versions. A sha-… tag never changes.

To push by hand instead (for example before the repo is on GitHub), run docker login -u <docker-user> with the Read & Write token as the password, then:

docker build --target http -t <docker-user>/chessbuddy-engine:manual-1 -f docker/mcp-stockfish.Dockerfile docker
docker build -t <docker-user>/chessbuddy-web:manual-1 .
docker push <docker-user>/chessbuddy-engine:manual-1
docker push <docker-user>/chessbuddy-web:manual-1

Docker Desktop on Windows builds linux/amd64, which Container Apps needs. On an Apple Silicon Mac, add --platform linux/amd64 to both builds.

4 Create the environment and the engine app

  1. Search the portal for Container Apps, then Create → Container App.
  2. Basics
    • Resource group: Create new → chessbuddy-rg
    • Container app name: chessbuddy-engine
    • Deployment source: Container image
    • Region: the same region as your Azure SQL database
    • Container Apps environment: Create new → chessbuddy-env. Choose Consumption only if offered; with Workload profiles, use only the Consumption profile (Dedicated profiles cost money). Zone redundancy: Disabled. Monitoring → Logs destination: Don't save logs (Log Analytics bills per GB; the live log stream still works). Networking: no virtual network.
  3. Container
    • Untick Use quickstart image.
    • Image source: Docker Hub or other registries · Image type: Private, even though the repository is public. Docker Hub limits pulls without signing in per IP address, and Container Apps shares its addresses with other Azure customers, so anonymous pulls can fail.
    • Registry login server: docker.io · user name: <docker-user> · password: the container-apps read-only token from step 3
    • Image and tag: <docker-user>/chessbuddy-engine:sha-<commit>, with the tag from the CI run summary
    • CPU and Memory: 1 CPU core, 2 Gi
  4. Ingress: Enabled · Ingress traffic: Limited to Container Apps Environment · Ingress type: HTTP · Target port: 8080
  5. Review + create → Create, then Go to resource.
  6. Application → Scale: Min replicas 0, Max replicas 2. Add a scale rule: name http-concurrency, type HTTP scaling, Concurrent requests 2. Save.
  7. On Overview, copy the Application Url. It contains .internal.; opening it in your browser gives a 404, which shows it's private.

At least two engines: one replica already runs two engines side by side (ENGINE_POOL_SIZE=2, set in the image). With the scale rule, a third simultaneous request starts a second replica, so up to four engines run at once. For more engines per replica, add the environment variable ENGINE_POOL_SIZE (and give it more CPU); for more replicas, raise Max replicas. The gateway is stateless, so any replica can answer any request.

The web app grades one move at a time by default, so a game review keeps one engine busy and leaves the other for the bot. To review faster, set GRADING_ENGINES on the web app (step 5) to grade that many moves at once; more engines at once uses the free grant faster.

5 Create the web app

  1. Create → Container App again. Basics: resource group chessbuddy-rg, name chessbuddy-web, same region, environment chessbuddy-env.
  2. Container: the same registry settings as the engine (Private, docker.io, the read-only token), image <docker-user>/chessbuddy-web:sha-<commit>, CPU and Memory 0.25 CPU / 0.5 Gi. Under Environment variables (Source: Manual entry) add:
    NameValue
    ENGINE_URLThe engine's Application Url from step 4 plus /mcp, e.g. https://chessbuddy-engine.internal.<id>.<region>.azurecontainerapps.io/mcp
    API_PORT3001
    COACH_MODELclaude-haiku-5-5 (cheapest) or claude-sonnet-5-5
    COACH_EFFORTlow or medium
    ANALYSIS_DEPTH16
    GRADING_ENGINESOptional, default 1: how many moves are graded at once, for example while reviewing a game. Each grade uses one of the engine's processes; a replica runs 2, so more requests at once, the bot's move included, start a second engine replica (step 4).
  3. Ingress: Enabled · Ingress traffic: Accepting traffic from anywhere · HTTP · Target port 3001 · insecure connections off.
  4. Review + create → Create.
  5. Application → Scale: Min 0, Max 1. One replica keeps the analysis cache and the sign-in attempt limit in one place.

6 Add the secrets

chessbuddy-engine

  1. Settings → Secrets → Add: key engine-token, type Container Apps secret, value = your engine token.
  2. Application → Containers → Edit and deploy, select the container, Environment variables → Add: ENGINE_TOKEN, Source Reference a secret, engine-token. Save → Create.

chessbuddy-web

  1. Settings → Secrets: add engine-token, session-secret, sql-connection-string, anthropic-api-key and, if you made one, lichess-token.
  2. Edit and deploy → container → add these variables, each with Source Reference a secret. Save → Create.
Variable (web app)SecretWhy
ENGINE_TOKENengine-tokenMust match the engine's token
SESSION_SECRETsession-secretWithout it, every restart (each cold start) signs you out
SQL_CONNECTION_STRINGsql-connection-stringAccounts other than the owner, in Azure SQL. Without it only the owner can sign in

7 Sign in and test

  1. Open chessbuddy-web → Overview → Application Url. After a quiet spell the first load takes a few seconds while the container starts.
  2. Sign in as kviiilyn37_ with the default password, or your own once step 10 is done. The owner's sign-in doesn't touch the database, so it's quick even while the database is paused. Other accounts' first sign-in after a pause can take up to a minute (the screen says so).
  3. The top bar should show Engine ready and your username. Play a move: it gets graded and the bot answers.

If something is off, Monitoring → Log stream shows each container's output, and Application → Revisions and replicas shows whether a revision is Running or Failed. The web app logs Accounts: Azure SQL, where the owner's password hash comes from, and Engine: https://…/mcp on startup.

8 Set a budget alert

Search for Cost Management → Budgets → Add: scope your subscription, reset period Monthly, amount $5, alerts at 50% and 100% of actual cost to your email. A budget only warns; it doesn't stop anything.

In the SQL database, keep auto-pause until next month as the behavior when the free limit is reached (switching to "continue with charges" can't be undone), and consider an alert on the Free amount remaining metric.

9 Deploy updates automatically

After this one-time setup, every push to master deploys itself. The CI run gets a third job, Deploy to Azure Container Apps. It points both apps at the run's sha-… tag (engine first), which creates a new revision of each, then waits until the web app's /api/health reports the new commit. GitHub signs in to Azure with a short-lived token (a federated credential), so no Azure password or secret is stored anywhere.

In Azure

  1. Search the portal for Microsoft Entra ID → App registrations → New registration. Name chessbuddy-github, Supported account types: single tenant (this organizational directory only), no redirect URI → Register. On its Overview, copy the Application (client) ID and the Directory (tenant) ID.
  2. In the registration, open Certificates & secrets → Federated credentials → Add credential. Federated credential scenario: GitHub Actions deploying Azure resources. Organization: your GitHub user, with the same capitals, Repository: ChessBuddy, Entity type: Branch, GitHub branch name: master, Name: chessbuddy-master → Add. These must match the repo exactly, or the sign-in is refused.
    • The form also asks for Organization ID and Repository ID, GitHub's numeric IDs, which don't change if you rename anything. Open https://api.github.com/repos/<github-user>/ChessBuddy in a browser: the first "id" is the repository ID, and "id" under "owner" is the organization ID (for a personal account, your user's ID).
    • The Subject identifier then reads repo:<github-user>@<owner id>/ChessBuddy@<repo id>:ref:refs/heads/master. GitHub uses this format for repositories created after 15 July 2026. An older repository still sends repo:<github-user>/ChessBuddy:ref:refs/heads/master unless you turn on immutable subject claims in its OIDC settings.
  3. Open the resource group chessbuddy-rg → Access control (IAM) → Add → Add role assignment. On the Privileged administrator roles tab pick Contributor → Next. Assign access to: User, group, or service principal → Select members → chessbuddy-github → Review + assign. The role covers only this resource group.
  4. Copy your Subscription ID from Subscriptions.

In GitHub

In the repo's Settings → Secrets and variables → Actions, add:

NameWhereValue
AZURE_CLIENT_IDSecretApplication (client) ID
AZURE_TENANT_IDSecretDirectory (tenant) ID
AZURE_SUBSCRIPTION_IDSecretSubscription ID
ACA_RESOURCE_GROUPVariablechessbuddy-rg. The deploy job is skipped while this is missing.

Then push to master, or re-run the latest CI run (Actions → CI → Run workflow). The run's summary lists the new revisions.

The job expects the container apps to be named like the images, chessbuddy-engine and chessbuddy-web, and keeps their registry credentials, secrets and environment variables. Each deploy briefly starts both apps, which uses a minute or two of the free grant. Only pushes to master deploy; pull requests and v* tags don't.

To deploy by hand instead, open Application → Containers → Edit and deploy in an app, select the container, change the tag to a sha-… tag from Docker Hub, then Save → Create. If you change ENGINE_TOKEN, update the secret in both apps.

10 Set the owner's password

The owner account kviiilyn37_ isn't in the database: the web app checks its password against a hash it already has, so the owner's sign-in never wakes the database. The default hash is in server/auth/users.ts, and the repo is public, so a weak default password could be cracked offline. Give the web app the hash of a strong password as a secret instead; it's never published.

  1. Make the hash locally: 
    npm run password:hash -- "<new password>"
  2. In chessbuddy-web → Settings → Secrets → Add: key owner-password-hash, type Container Apps secret, value the whole line the script printed (it starts with scrypt$).
  3. Application → Containers → Edit and deploy, select the container, Environment variables → Add: OWNER_PASSWORD_HASH, Source Reference a secret, owner-password-hash. Save → Create.

The new revision logs Owner kviiilyn37_: password hash from OWNER_PASSWORD_HASH. If the value isn't a hash from the script, the revision refuses to start rather than fall back to the default password; its log stream says why, and the previous revision keeps serving. The deploy job in step 9 keeps the app's secrets and environment variables, so later deploys keep the password. To change it again, update the secret and restart the revision (Revisions and replicas → Restart).

Sessions already signed in stay valid until they expire (7 days). To sign everyone out at once, change session-secret and deploy a new revision.

Changing the owner's row in chessbuddy.Users has no effect: the server ignores any database row named kviiilyn37_. If an older version of the app created one, you can delete it.

11 Add other accounts

There's no sign-up: other accounts are rows in chessbuddy.Users. They aren't VIP, so they can use Haiku and Sonnet but not Opus, which only VIP accounts (the owner) may use.

  1. Make the account's password hash locally: 
    npm run password:hash -- "<their password>"
  2. Open scripts/add-user.sql from the repo (it's the script below) and put the username and that hash in the two values at its bottom.
  3. In the portal open the SQL database → Query editor, sign in, paste the whole script and Run.
IF SCHEMA_ID(N'chessbuddy') IS NULL EXEC(N'CREATE SCHEMA chessbuddy');
IF OBJECT_ID(N'chessbuddy.Users', N'U') IS NULL EXEC(N'CREATE TABLE chessbuddy.Users (
  Id INT IDENTITY(1, 1) PRIMARY KEY,
  Username NVARCHAR(64) NOT NULL UNIQUE,
  PasswordHash NVARCHAR(255) NOT NULL,
  IsVip BIT NOT NULL DEFAULT 0,
  CreatedAt DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
)');
IF COL_LENGTH(N'chessbuddy.Users', N'IsVip') IS NULL EXEC(N'ALTER TABLE chessbuddy.Users ADD IsVip BIT NOT NULL DEFAULT 0');

EXEC sp_executesql
  N'INSERT INTO chessbuddy.Users (Username, PasswordHash, IsVip) VALUES (@username, @passwordHash, 0)',
  N'@username NVARCHAR(64), @passwordHash NVARCHAR(255)',
  @username = N'<username>',
  @passwordHash = N'<hash from npm run password:hash>';

The first three statements create the schema and the table when they're missing, and add the IsVip column to a table created before it existed; on a database that's already set up they do nothing. The insert goes through sp_executesql so it compiles after the column exists, which lets the whole script run as one batch.

To change an account's password, or make it VIP, run one of these. Changes apply from the account's next sign-in:

UPDATE chessbuddy.Users SET PasswordHash = N'<new hash>' WHERE Username = N'<username>';
UPDATE chessbuddy.Users SET IsVip = 1 WHERE Username = N'<username>';

Costs and limits

  • Container Apps free grant (per subscription, each month): 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests. You're billed only while a replica runs.
  • With the engine at 1 vCPU / 2 Gi and the web app at 0.25 / 0.5 Gi, that's roughly 40 hours of play a month with one engine replica. A second engine replica uses it up faster. Past the grant, a rough estimate is about 15¢ an hour.
  • Replicas stay up a few minutes after the last request before scaling to zero. The app only checks status while its tab is visible, so a tab left in the background doesn't keep the containers running.
  • Keeping replicas always on (Min replicas above 0) goes past the free grant: two always-on engine replicas would be roughly $40 a month.
  • Azure SQL free offer: 100,000 vCore-seconds a month. Only the sign-in of an account other than the owner touches the database, and connections close after 30 seconds idle, so it can pause.
  • Claude: only Explain and questions to the coach cost money. Haiku is the cheapest model; Opus, the dearest, is only for VIP accounts.

Troubleshooting

What you seeLikely cause and fix
"Couldn't reach the account database"The Azure services exception in step 2 is off, the connection string is wrong, or the database used up its free amount and is paused until next month. The web app's log stream shows the SQL error.
"Engine unavailable" in the top barENGINE_URL must be the engine's internal https://… URL ending in /mcp. "Unauthorized" in the message means ENGINE_TOKEN differs between the apps. Check the engine revision is Running.
Signed out after every cold startSESSION_SECRET isn't set on the web app.
"Too many failed sign-ins"Five wrong passwords from your address. Wait 15 minutes, or restart the web app's revision.
The web revision fails with "OWNER_PASSWORD_HASH must be a hash"The owner-password-hash secret isn't the line npm run password:hash printed. Paste the whole line, starting scrypt$, without quotes (step 10).
"Opus 5.5 is only for VIP accounts"The account isn't VIP: pick Haiku or Sonnet, or set its IsVip to 1 (step 11) and sign in again.
Revision failed: image pull errorThe tag doesn't exist (check the repository's Tags on Docker Hub), the registry credentials are missing or wrong so Docker Hub's anonymous pull limit applies, or the image was built for ARM.
"The TargetPort 3001 does not match the listening port 8080" on chessbuddy-webThe web app is running the engine image: only chessbuddy-engine listens on 8080. Set the image to <docker-user>/chessbuddy-web:sha-… (step 5), and make sure API_PORT is 3001 or not set. The log stream should show ChessBuddy server on http://localhost:3001, not Engine gateway on port 8080.
CI fails at "Check Docker Hub settings"The DOCKERHUB_USERNAME variable or the DOCKERHUB_TOKEN secret is missing in the GitHub repo (step 3).
CI fails at "Sign in to Docker Hub" or the push is deniedThe token is wrong, expired, or read-only. Generate a Read & Write token and update the secret.
Deploy fails at "Sign in to Azure": no matching federated identity recordThe federated credential's organization, repository or branch doesn't match the repo, or one of the AZURE_* secrets is wrong (step 9).
Deploy fails with AuthorizationFailedThe Contributor role on chessbuddy-rg is missing or hasn't applied yet. Wait a few minutes and re-run the job.
Deploy fails with ResourceNotFoundA container app isn't named chessbuddy-engine / chessbuddy-web, or ACA_RESOURCE_GROUP names another group.
Deploy fails at "Wait for the new web app to answer"The new web revision didn't start. Revisions and replicas and the log stream show why; the previous revision keeps serving meanwhile.
404 when opening the engine URLExpected: the engine only answers apps inside the environment.
First request after a break is slowExpected: containers start from zero and the database may be resuming.
Local development is unchanged: npm run dev still starts the engine with docker run -i unless ENGINE_URL is set. Settings are listed in the README.
